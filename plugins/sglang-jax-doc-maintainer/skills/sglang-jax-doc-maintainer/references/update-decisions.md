# 更新决策

编辑前必须为每个候选文档选择一个决策。决策应基于当前代码、测试、配置、既有文档和用户确认，而不是 PR 文案本身。

## 决策类型

| 决策 | 使用条件 |
|---|---|
| 不更新 | 变化不影响已文档化架构事实，或只是 test/CI/format/generated/refactor-only |
| 信息不足，需人工确认 | diff 不完整、base 不明、证据冲突、changed-files-only 语义不足 |
| 段落融入 | 现有结构正确，新事实可自然融入已有段落、表格或列表 |
| 章节重构 | 旧结构会导致补丁化、重复或冲突，需要重排受影响章节 |
| 新增章节 | 新内容属于 01-13 中某个既有文档，但需要独立小节承载 |
| 删除过期陈述 | 文档陈述与当前代码冲突，且新事实可验证 |
| 重命名 / 移动引用更新 | 文件、symbol 或配置被 rename/move/delete，文档引用过期 |
| 配置参考更新 | config field、default、CLI、env var、schema 或调用点改变 |
| 图表候选，仅计划 | 图表可能过期，但未获得单独确认前不得编辑 |
| 新增独立文档 | 默认禁止；只有用户明确授权后可计划 |

## 不更新

适用场景：

- 变化只影响测试、CI、格式化、缓存设置或 generated files。
- 变化是未被文档表达的 private helper 或内部重构。
- 既有文档已经准确描述该行为。
- 变化实现细节低于架构文档目标粒度。
- changed-files-only 输入不足以判断语义变化。

必须输出候选文档和不更新原因。

## 信息不足，需人工确认

适用场景：

- base branch 不明确。
- PR / diff 无法访问。
- diff 太大且无法分批确认语义。
- 只有 changed files，没有 diff 或代码上下文。
- 当前代码与既有文档冲突，但无法判断设计意图。
- 文档需要写 rationale、性能、兼容性或支持状态，但缺少证据。

输出阻塞原因和需要用户提供的信息，不得编辑。

## 段落融入

适用场景：

- 新行为扩展了既有概念。
- 既有章节结构仍然正确。
- 表格、列表或段落可以自然吸收该变化。

必须有证据表支撑新事实。优先改写已有内容，而不是追加脱节 note。

## 章节重构

适用场景：

- 新行为改变了既有概念的解释方式。
- 旧表述与当前代码冲突。
- 简单追加会让章节补丁化。
- 如果已有 sibling concepts 与新增概念共享分类轴，应先尝试抽象父级概念；计划必须说明候选父级概念、共同分类轴、覆盖成员、边界和不纳入项，再决定新建/重构父级章节、融入既有结构或不提升。
- 横向概念需要先建立或修正 taxonomy。

只在文档结构确实阻碍准确表达时重构。不得因为想统一风格而大段重写无关内容。

## 新增章节

适用场景：

- 该 feature 独立到需要自己的概念、流程和细节。
- 它仍属于某个 01-13 主文档。
- 放进现有小节会让该小节过宽。
- 之前分散的子特性形成可识别 feature family。

计划必须说明父文档、拟新增标题、证据来源和为什么不是段落融入。

## 新增独立文档（默认禁止）

01-13 之外的新文档、导航、sidebar 或索引修改默认禁止。只有用户明确授权后才可计划。

如果认为必须新增独立文档，计划中必须列出：

- 为什么 01-13 中没有合适承载位置。
- 替代方案：在 01-13 中新增章节或重构现有章节。
- 需要新增或修改的导航 / cross-link。
- 等待用户授权的明确问题。

## 图表候选（需单独确认）

适用场景：

- 既有图表展示了过期模块关系、数据流或控制流。
- 新概念难以只靠文字解释清楚。
- 当前文档引用了受变化影响的图表。

可以在计划中列出图表候选，但未获得用户单独确认前不得编辑 SVG、Excalidraw、图片或图表源文件。

## 同级层级与细节克制

PR 引入的新 symbol、helper、内部容器或局部字段，不能因为是新增代码就自动进入主数据结构、核心特性、backend family、mode family 或 taxonomy 的同级列表。编辑计划必须先判断它与目标列表中的既有条目是否处于同一抽象层级。

判定规则：

- 如果目标列表列的是主数据结构、核心组件、一级特性或 sibling concept，只能加入同级概念。
- 如果新增内容是某个主结构的内部子容器、辅助字段、局部中间表示或实现 helper，应放在父概念段落中简要说明，或选择不更新。
- 如果理解架构必须知道该细节，计划必须写明它的父概念、为何不能省略，以及如何避免把它表述成同级概念。
- 如果新增细节会让当前 diff 的实现篇幅超过同级旧概念，应压缩为抽象描述、表格补充或交叉链接，不得扩写成改变原文档重心的新小节。

方案充分性门禁中必须检查 peer-level mismatch 和 over-expansion risk。只要存在非同级内容被计划放入同级列表，或新增代码细节篇幅/层级会扭曲既有架构结构，结论必须是 `structurally-incomplete` 或 `over-update-risk`，不得请求用户确认执行。

## 横向架构概念与 taxonomy

本节中的 `taxonomy` 是内部结构判断术语，表示文档中用于组织同级概念的分类容器。最终正文不得直接沿用该内部标签；必须转换为从当前证据推导出的读者可理解专业技术术语。示例只用于说明命名形态，不构成固定分类；若存在项目内既有术语或业界标准术语，优先使用既有/标准术语；若没有成熟术语，使用准确的描述性名词短语。

以下情况触发 overview 和 sibling-consistency 检查：

- 新概念需要与既有同级概念比较。
- 分散章节需要共享 taxonomy、边界或流程说明。
- 没有父级说明时，直接模块文档会像补丁拼接。
- 读者需要理解多个策略、backend、mode 或资源管理路径之间的关系。

横向概念触发不等于必须重构。必须比较至少两个放置方案：

- 扩展既有 taxonomy。
- 新增或重构 taxonomy 小节。
- 只做局部段落 / 表格行更新。
- 不更新并说明证据不足或现有结构已足够。

如果选择局部更新，必须说明为什么不会造成孤立 feature、过度聚焦当前 diff 或 sibling 失衡。若前文已经判断 overview 缺少或不足以承载该概念族的 taxonomy 容器，且新增概念与既有 sibling concepts 共享分类轴，P1 必须计划在 overview 或父文档新增/重构读者可见父级章节，列出父章节标题、覆盖成员、共同分类轴、边界和不纳入项、overview 与子文档分工；不能仅用段落融入、feature 表行或“章节重构 + 新增行/段落”替代。若不新增/重构父级章节，feature family / taxonomy 结论必须是 `structurally-incomplete`、`insufficient-evidence` 或 `over-update-risk`，不得请求用户确认执行。

## 方案充分性门禁

输出可执行更新计划前，必须证明方案语义充分、证据充分、结构合适、范围最小。该门禁适用于所有影响类型，不只适用于横向 taxonomy。

| 影响类型 | 必须覆盖的问题 |
|---|---|
| config / default / CLI | 字段名、默认值、alias、约束、调用点、配置参考位置 |
| control flow | 入口、状态转移、生产者、消费者、流程文档位置 |
| data flow | 数据结构、生产者、消费者、中间表示、跨文档一致性 |
| rename / delete | 反向搜索旧引用、删除或移动后的替代事实 |
| feature family / taxonomy | 概念族、sibling concepts、候选父级抽象、共同分类轴、overview 容器、父级章节标题、覆盖范围、边界和不纳入项、overview 与子文档分工、放置方案 |
| abstraction level / detail proportionality | 新增内容是否与目标列表同级、是否属于父概念细节、篇幅是否相对 sibling concepts 克制、读者可见术语是否专业 |
| public behavior / support status | 可见行为、限制、支持状态、不能写的推断 |

每个适用类型必须给出 `sufficient`、`insufficient-evidence`、`structurally-incomplete`、`scope-unclear` 或 `over-update-risk`。只要存在非 `sufficient` 的适用项，就不得请求用户确认执行；必须先修正计划、缩小为“不更新/信息不足”，或请求补充证据。

方案充分性表中的 `taxonomy`、`evidence`、`Unknown` 等字段名只用于分析报告和计划，不是最终正文标题、表格列名或图表标签。最终正文必须使用读者可见的专业术语或准确描述性名词短语。

同时必须说明最小正确方案：为什么当前更新是必要的，为什么更小方案不足，为什么更大重构会过度。“最小”指能正确承载读者心智模型、父级概念、sibling 关系和跨文档分工的最小充分方案，不是最少行数或最小侵入补丁。

## 01-13 全局一致性

每个编辑计划至少判断：

- 是否影响 `01-architecture-overview.md` 的系统模型。
- 是否影响 `13-configuration-reference.md` 的 flag / default / config 分类。
- 是否影响已有 cross-link。
- 是否造成同一概念在多个文档中重复但不同步。
- 是否需要同步术语。
- 是否需要列出不更新的相关文档及原因。
