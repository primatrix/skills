# sglang-jax 文档写作风格

写作目标是中文架构文档，而不是 PR 摘要、release note 或实现流水账。

## 风格规则

- 以中文为主。
- 保留标准英文技术术语，例如 Attention Backend、KV Cache、Scheduler、Pallas、JIT、LoRA。
- 文件名、类名、函数名、配置字段和命令使用反引号。
- 优先使用解释性段落，并辅以表格和有序流程列表。
- 标题使用简洁名词短语，并优先使用业界或项目中已有的专业术语；没有成熟术语时，再使用准确的描述性名词短语。
- 最终文档必须使用读者可理解的领域术语，不得泄漏计划、评审或分析过程中的内部标签。`taxonomy`、`evidence`、`inference`、`Unknown`、`门禁`、`checklist`、`Plan ID`、`决策类型` 等词只用于分析报告或执行检查；除非它们本身就是当前技术领域的标准术语，否则不得进入最终正文、标题、表格列名或图表标签。
- 避免营销式语言和无依据形容词，例如“显著提升”“大幅优化”“完整支持”。
- 避免教程式第二人称。

## 去除 PR 痕迹

最终文档不得包含 PR 编号、commit hash、代码行号、作者、reviewer，或”this PR adds””本次变更””新增于某 PR”等说法。

PR metadata 可以出现在分析报告、更新计划或完成总结中，但不能出现在最终 markdown 文档中。

### 禁用中文模式（任一命中即违规）

正文中出现以下任一中文模式即视为违规，不得在写入最终文档前保留：

- “由 PR #XXXX 引入”
- “PR #XXXX 把 X 拆 / 合并 / 重构成 Y”
- “PR #XXXX 新增 / 删除 / 修改”
- “在 PR #XXXX 中实现”
- “本次 / 本次变更 / 本轮 / 新增于 / 新引入”
- “commit XXXXXXX 引入”
- “见 #1234” / “参考 PR #1234”
- “最近的 PR” / “近期 PR” / “上一个 PR”
- “目前正在重构” / “近期” / “未来计划” / “将在下个版本中”

### 强制改写规则：evidence 含 PR / commit / issue → 正文必须改写为稳定状态描述

进入 confirmed-edit 阶段时，第一步是把 plan 中每条标注 PR 编号、commit hash、issue 链接、行号、作者名、时间锚点的 evidence 改写为”代码现在是什么”的稳定状态描述。改写后的措辞才是写入正文的初稿。

| Evidence 来源 | 禁止写法 | 必须改写为 |
|---|---|---|
| PR 描述某 class 在该 PR 中引入 | “X 由 PR #XXXX 引入” / “X（由 PR #XXXX 引入）” | “X 由 `<file>` 定义” / “X（`<file>`）” |
| PR 描述某次类层级重构 | “PR #XXXX 把 EAGLEWorker 拆成两层” | “Spec Worker 由两层抽象组成：`BaseSpecWorker` 与 `BaseDraftWorker`” |
| commit message 描述某 bug 修复 | “commit abc1234 修复了 KV 越界” | “KV 分配逻辑使用 `ALLOC_LEN_PER_DECODE` 上界，避免越界” |
| issue 讨论某设计权衡 | “issue #1234 决定了 X 的设计” | “X 当前选择 Y，权衡见 `<file>`” |
| 文件 line N 含某 helper | “见 `<file>` 第 N 行” | “X 在 `<file>` 中以 helper 形式存在” |

未完成此改写就直接编辑文档的，视为违反 confirmation protocol，必须回退该次编辑并重写。

## 证据到措辞

| 证据 | 可以写 | 不得写 |
|---|---|---|
| 当前代码存在 class / function | “实现中包含 X 路径 / X 组件” | “为了提升可扩展性引入 X” |
| 配置字段和默认值可验证 | “`flag` 默认值为 ...” | “推荐所有场景启用” |
| PR body 声称性能提升 | “PR 描述声称性能变化，需确认” | “性能显著提升” |
| 测试覆盖某行为 | “测试覆盖该行为” | “生产稳定支持该行为” |
| 外部资料描述通用模式 | “通用背景中该模式通常...” | “sglang-jax 因此具备该能力” |

性能、稳定性、兼容性、支持状态、设计意图和默认启用状态必须有当前代码、benchmark、既有文档或用户确认支撑。

## 系统性融入

不要简单追加新内容。当以下编辑能让文档更连贯时，优先采用：

- 改写既有段落以纳入新概念。
- 更新既有表格行，或在既有表格内新增行。
- 合并重复的新旧解释。
- 调整受影响章节内的小节顺序。
- 删除与当前代码冲突的过期表述。
- 当概念在其他文档中展开时，添加交叉链接。

如果单点添加会让章节显得补丁化，应提出聚焦的章节重构；但不得因为当前 diff 新鲜就过度重写。

## 范围和深度

从整套架构文档规划新增内容，而不是只根据代码 diff 大小判断。

新增详细小节前，先判断：

- 读者在当前文档层级需要回答哪个架构问题。
- 该细节属于当前文档、另一个既有文档、新章节，还是不需要文档更新。
- 实现细节应被概括、移入表格，还是因不影响架构理解而省略。
- 新增文本是否会让章节相比既有核心概念过度聚焦当前 feature。

最终篇幅比例应匹配其架构重要性、用户可见行为，以及与周边模块的关系。

## 同级层级与新增细节克制

架构文档中的列表和 taxonomy 必须保持抽象层级一致。新增代码中的 helper、内部容器、字段或中间表示，不得与既有主数据结构、核心特性、backend、mode 或策略并列，除非它本身已经是同级架构概念。

写作时优先使用父概念承载实现细节：例如内部 per-rank 容器应描述为某个 Batch 结构在 DP 场景下的组织方式，而不是放入“核心数据结构”并列清单。若某个细节低于当前文档层级，应省略或用一句话嵌入父段落。

新增 PR 代码越多，越要克制最终文档篇幅。不要因为 diff 中出现大量新函数或字段，就把实现流水账扩写进架构文档；最终新增内容的深度应由读者理解架构所需的问题决定，而不是由代码新增量决定。

## 横向概念与 sibling balance

当同一上层 feature 的多个分支逐渐累积时，不要把每个分支当成孤立补丁。必须重新评估父概念，并考虑 summary section、taxonomy 表格或现有章节重构。

如果新增或更新父级 overview，必须检查同一 feature family 的子文档。保持 sibling concepts 在术语、深度、章节位置和抽象层级上的平衡。

如果选择不平衡处理，必须说明理由，例如新概念用户可见性更高、旧概念已在其他文档充分展开，或当前证据不足。

## 外部调研

外部调研只能进入分析报告的“背景参考”。最终项目文档只能写当前代码、既有文档或用户确认支持的事实。

允许的通用背景：

- Block sparse Attention backend 通常通过限制可见位置来降低长上下文 attention 成本。
- Paged KV Cache 设计通常通过固定大小 page 管理来降低分配碎片。

需要项目证据：

- sglang-jax 在某个命名场景提升吞吐。
- sglang-jax 默认启用某个 backend。
- sglang-jax 支持某个模型、dtype、device 或配置。

如果最终文档确实需要引用通用背景，必须避免暗示 sglang-jax 已实现外部资料中的全部能力。

## 新章节和新文档

新章节必须说明它在 01-13 中哪个父文档下、如何与既有模块交互，以及相关实现文件。

新独立文档、导航、sidebar 或索引修改默认禁止，只有用户明确授权后才可执行。

## 图表文本

对于图表：

- 展示文件名或模块名，不展示代码行号。
- 不添加分区编号。
- 防止长标签或代码块溢出。
- 图表术语必须与正文一致。
- 未获得单独确认前不得修改图表文件。
