# 横向架构 taxonomy 规则

当变更影响跨模块 feature family、backend family、资源策略、执行模式、调度策略、缓存策略等横向概念时使用本规则。

## 父级抽象发现

当新增概念与既有 sibling concepts 共享同一分类轴时，必须主动尝试抽象父级概念，而不是只围绕新增概念做局部补丁。

触发条件：

- 新增概念与至少两个既有概念在同一维度上可比较。
- 既有文档分散描述这些 sibling concepts，但没有父级章节解释它们的关系。
- 新增概念会让读者需要理解“这组机制如何分类、何时使用、如何组合或互斥”。
- 新增概念会使现有列表从若干孤立项变成可命名的 concept family。

必须输出：

- 候选父级概念：从当前证据推导出的读者可见名称；示例只说明命名形态，不构成固定分类。
- 共同分类轴：这些 sibling concepts 基于什么维度同类，例如资源管理路径、执行阶段、backend 选择、切分维度。
- 覆盖的 sibling concepts：新增概念和既有概念。
- 边界和不纳入项：哪些相邻机制不是该父概念成员。
- 放置位置：overview、父文档或子文档。
- 结构动作：新建/重构父级章节、表格或列表；或说明现有结构足够。

若选择不提升为父级章节，必须说明为什么 sibling concepts 数量、读者心智负担、现有结构或证据不足以支撑父级抽象。不能用“只改新增概念更小”作为唯一理由。

## 触发条件

满足任一条件即触发：

- 跨越三个或更多文档或子系统。
- 改变读者对系统组织方式的心智模型。
- 在既有概念旁边引入同级概念。
- 新增需要与既有概念比较的轴、分类、生命周期阶段、backend family、资源策略或执行模式。

## 必填判断

- 概念族：所属更大架构家族。
- 候选父级概念：新增概念与 sibling concepts 可上升出的读者可见父概念。
- 共同分类轴：这些 sibling concepts 的同类维度。
- 既有同级概念：已被文档描述的相关机制。
- Overview 放置位置：应出现在哪个 overview 或父文档中。
- Taxonomy 容器状态：已存在且足够 / 已存在但不足 / 不存在 / 不适用。
- 放置方案：至少两个方案。
- 最终选择：选择结果和理由。
- 计划动作：最终选择必须反映到更新计划。
- 不重构理由：若只做局部更新，说明为什么不需要新增/重构 taxonomy，且不能与“容器不存在/不足且需要 taxonomy”的判断矛盾。

## 合法结果

- 扩展既有 taxonomy。
- 新增或重构 taxonomy 小节。
- 只做局部段落 / 表格行更新，并说明不重构理由。
- 不更新，并说明当前文档已足够或证据不足。
- 信息不足，询问用户。

## Plan-only 自洽门禁

在输出更新计划并请求用户确认前，必须检查横向概念判断与计划动作是否一致：

- 若最终选择“新增或重构 taxonomy 小节”，计划中必须出现对应的结构性动作：目标文档、拟新增/重构标题或表格、覆盖的 sibling concepts、共同分类轴、边界和不纳入项、overview 与子文档分工、交叉链接位置。
- 若判断 taxonomy 容器“不存在”或“已存在但不足”，且新增概念与既有 sibling concepts 共享分类轴，计划必须在 overview 或父文档中新增/重构读者可见父级容器，并列出标题、覆盖的 sibling concepts、共同分类轴、边界和不纳入项、overview 与子文档分工；只做 feature 表行、局部段落或措辞调整必须判为计划矛盾，不能请求用户确认。
- 若判断 taxonomy 容器“不存在”或“已存在但不足”，但计划只做 feature 表行、局部段落或措辞调整，必须把这视为计划矛盾；先改计划或明确改选局部更新并写出证据充分的不重构理由。
- 若选择局部更新，理由必须说明为什么现有结构足够、为什么不会形成孤立 feature、为什么不会让当前 diff 比 sibling concepts 过度突出。
- 不能把“等待用户确认”作为解决计划矛盾的方式；用户确认前交付的计划本身必须自洽。

## 反模式

- 只因为当前 diff 新增 feature，就让它比同级概念更详细。
- 只追加 release-note 风格段落。
- 需要父级 taxonomy 时只更新子文档。
- sibling concepts 已存在，却新增孤立小节。
